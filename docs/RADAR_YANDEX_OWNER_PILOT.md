# Ограниченный пилот Yandex Search API

Это прежний отдельный режим с пакетом из двадцати запросов. Для постоянного
ключа и отдельных ручных заданий используется
[постоянное подключение](RADAR_YANDEX_PERMANENT_CONNECTION.md); инструкция ниже
не является его активацией.

`radar_yandex_pilot.py` — отдельный запуск по указанию владельца. Он разрешает
только обычный текстовый поиск по точному плану после независимой проверки кода
и установки локального activation pin. Сам verifier не создаёт допуск.

Общий MDOS не ратифицируется. Старые `fetch_yandex_search`, `run_yandex_search`,
`radar_yandex_transport run` и fixed RC1 сохраняют отказ. Остальные источники,
CRM, контакты, отправки, публикация и расписание не входят в разрешение.

## Что ограничено

- Точный Yandex Search API v2 endpoint, каталог по SHA-256, 20 исходных запросов
  по пяти регионам из существующего плана. Свободные query/page не принимаются.
- Не более 100 попыток и 6000 копеек верхней оценки, минимум 49 копеек на попытку.
  Эти потолки не добавляют новые запросы к двадцати разрешённым. Сумма является
  локальным резервом, не счётом провайдера или гарантией неизменного тарифа.
- Срок допуска не более 24 часов. Временное хранение ответа — 24 часа;
  удаление выполняется существующей командой `purge`.
- Единственный журнал `pilot.sqlite` рядом с activation pin, с привязкой к
  физическому file ID и policy SHA-256. Другой файл с теми же байтами не подходит.
- Проверенная версия шести production-файлов, включая неизменённый fixed RC1.
  Изменение кода, папки исполнения или approval-пакета отзывает допуск.

## Как устанавливается допуск

В каталоге текущего пользователя ОС `.codex/local_state/TenderBot/yandex-pilot`
находятся отдельный журнал, каталог `dispatch-claims` и `activation.json`.
Корень определяется через профиль ОС; подстановка `HOME`/`USERPROFILE` в
окружении не меняет доверенную точку. Перенаправления/reparse paths запрещены.

До установки pin оператор готовит строгий JSON-пакет с policy, идентичностями
файла и каталога claims, точным корнем кода и его hashes. Пакет содержит:

1. Capture настоящего указания владельца с привязкой к согласованному scope.
2. Независимый `ACCEPT` на точные production hashes; reviewer отличается от owner.
3. Фактическую проверку биллинга (`ACTIVE`/`TRIAL_ACTIVE`), конфигурации Search API
   и точной идентичности ключа: service account ID, API key ID, scope
   `yc.search-api.execute` и SHA-256 ключа, без самого секрета. Эти поля входят в
   scope указания владельца. Это ещё не доказательство успешного HTTP.
4. Фиксированные даты, запрещённые эффекты и `mdos_ratification=false`.

Пакет с обязательной привязкой credential имеет версию
`radar-yandex-pilot-authority-v2`. Формат отдельного activation pin не менялся
и остаётся `radar-yandex-pilot-activation-v1`; его hash закрепляет точные байты
пакета v2, поэтому старый пакет v1 не принимается новым verifier.

После этих проверок отдельный data-only pin фиксирует SHA-256 точных байтов
пакета, policy, срок и путь. Его установка и readback — отдельный операторский
шаг. В CLI нет `--approved`, `--allow-live`, подмены времени или произвольного
пути к pin. Сам hash, поле роли владельца и синтетическая fixture доступа не дают.

`CAPTURED_OWNER_INSTRUCTION` — запись реального указания, а не электронная подпись.
Локальные файлы не защищают от злонамеренного процесса с теми же правами ОС,
ручного удаления claims или восстановления старой копии всего состояния.
Такое вмешательство требует отдельного расследования и не является restart.

## Порядок единственной отправки

Verifier проверяет pin, пакет, независимый review, код и срок; runner открывает
только закреплённый journal и проверяет точный запрос/folder до чтения ключа.
После проверки постоянных привязок verifier сохраняет наблюдаемое время в этом
journal даже при отказе по сроку. Поэтому новый процесс с более ранними часами
не восстанавливает уже наблюдавшийся просроченный допуск. Pin и receipts при
этой проверке не меняются.
Сохранённый точный ответ возвращается локально даже после STOP, пока действуют
pin, scope и срок хранения. Если ответа нет, STOP срабатывает до чтения ключа.
Для нового запроса отпечаток выбранного ключа проверяется до резерва; затем
отдельно коммитятся резерв и dispatch intent и создаётся одноразовый capability.

До выдачи capability создаётся уникальный постоянный claim-файл через
`O_CREAT | O_EXCL` с `fsync`. Он связывает request ID, intent, policy и body hash.
Повторная выдача того же intent, в том числе из другого процесса, запрещена.
Claims не удаляются после ошибки, crash или очистки поисковых ответов.

HTTP core потребляет только зарегистрированный capability и повторно проверяет
его привязки и отпечаток фактически переданного ключа непосредственно до
connect. Поддельный object, подмена ключа, изменённый body/request ID, второй
вызов, отозванный pin или просроченный capability не открывают сеть. Вызов core
без capability идёт через старый fixed RC1 и остаётся запрещённым.

Crash между claim и HTTP сохраняет расход и требует разбора; paid retry нет.
STOP запрещает новые intents. Одна уже выданная in-flight попытка может
завершиться после STOP. Эти ограничения не обещают отменить уже начатый HTTP.

## Запуск и проверка результата

Перед live нужен действующий платёжный аккаунт и отдельный ключ сервисного
аккаунта с ролью `search-api.webSearch.user`, scope `yc.search-api.execute` и
сроком пилота. Это соответствует [инструкции sync v2](https://aistudio.yandex.ru/ru/docs/search-api/operations/web-search-sync).
Ключ не передаётся в чат, публичный PR, аргументы команд или bundle. Runner
читает его из локального `YANDEX_SEARCH_API_KEY` только после допуска.

```powershell
python -B -X utf8 -m lead_factory.radar_yandex_pilot --bundle ABSOLUTE_APPROVED_BUNDLE_PATH --folder-id FOLDER_ID --request-index 0
```

Одна команда делает не более одной отправки. Сначала выполняется один реальный
контроль: проверяются HTTP-исход, запись intent/расхода, точный response hash,
разбор XML и повторное локальное чтение без нового HTTP. Только затем оператор
продолжает остальные разрешённые индексы с учётом исхода контроля.
Успешный JSON явно содержит `external_requests_this_run`: `1` для отправки и
`0` для локального replay, а `journal` сохраняет общий резерв и состояния.
Если HTTPS уже начат, timeout, HTTP-отказ или ошибка разбора дают безопасный
error JSON с `external_requests_this_run=1` и состоянием `UNCERTAIN`; отказ до
сети, включая неверный ключ, сообщает `0`. Путь и отпечаток ключа не выводятся.

Выдача остаётся материалом исследования: `capture_verified=false` не превращает
поисковый snippet в проверенный факт строительства. Сопоставление объекта,
участников, стадии и даты требует проверки первичного источника; импорт
выполняется отдельной ручной транскрипцией через существующий паспорт.

Параметры парсера, исходный план, локальные команды журнала и ограничения
хранения описаны в [подготовке Яндекса](RADAR_YANDEX_SEARCH_PREPARATION.md).
