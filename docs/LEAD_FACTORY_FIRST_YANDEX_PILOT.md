# Первый контрольный Yandex-пилот без DOM.РФ

Это контрольный протокол и предложение точного запроса. Он не разрешает
provider read, credential read, расход, CRM/contact или запуск расписания.
Общий потолок источников — 30 000 руб./месяц. DOM.РФ не покупать.

## Фактическая цепочка продукта

Аудит после интеграции активатора (PR #6, merge `807f3c5`, дерево
`b59f37ad4b00b2d7881b0f9d6d5b0a75c0ebbdc2`) подтвердил следующие границы:

| Этап | Код | Что ещё требуется доказать |
| --- | --- | --- |
| Поиск | `run_manual_yandex_search_accounted` → bounded accounting | Отдельный разрешённый реальный запрос и его receipt |
| Дедупликация | `build_review_queue` → `persist_yandex_review_batch` | Это уникальные ссылки `SUPPLIED_SEARCH_RESPONSE_UNVERIFIED`, а не лиды |
| Проверка объекта | `prepare_verified_radar_import` → `RadarWorkbenchImporter.import_bytes` | Проверенная оператором запись, первичные факты и одобренный SourcePassport |
| Стадия и участники | `ConstructionDemandRadar.ingest/assess` | Актуальные подтверждённые сведения об объекте, участниках и потребности |
| Действие менеджера | `RadarResearchWorkbench.assign/record_result` | Осмысленная задача, ответственный, срок и допустимый канал |
| Коммерческий результат | `ConstructionDemandRadar.record_feedback` | Подтверждение RFQ/КП/заказа документом или разрешённой системой учёта |

`review-decide APPROVE` завершает проверку ссылки. Оно не превращает ссылку в
канонический объект, не создаёт согласие на контакт и не доказывает сделку.
Разрешение на строительство, сниппет, публичный телефон и прогноз не являются
подтверждённой закупочной потребностью.

Ближайший обязательный операторский шаг закрывает
`source yandex-publish-evidence`: проверяет уже полученные реальные receipts
из fixed inbox и публикует exact evidence. Он не создаёт эти receipts и не
утверждает, что billing/API/credential проверены через внешнюю систему.

## Один точный контроль

- Предлагаемый неперсональный запрос: `строительство школы Краснодарский край фасад остекление`.
- Регион: `Краснодарский край`.
- Источник: только Yandex Search API через существующий native runner.
- Один job, один запрос, максимум и резерв 49 копеек. Без повторов после неопределённого результата.
- Raw retention: 24 часа; draft действует шесть часов. Истечение срока требует нового допустимого процесса, а не изменения старых байтов.
- После code freeze подготовить один inert draft с новым idempotency key, сохранить job/draft/scope hashes и время окончания. Не готовить draft на изменяемом runtime.

Перед любым запуском нужны реальные owner scope, независимый ACCEPT точного
code map, свежие billing/API/credential observations, успешная публикация и
активация. Выполнять их по
[инструкции evidence](RADAR_YANDEX_ACTIVATION_EVIDENCE.md) и
[runbook](SAFE_LEAD_FLOW_LAUNCH_RUNBOOK.md). Реальный `run-one` остаётся отдельным
явным решением по конкретному job. Тестовые receipts для него непригодны.

## Проверка результата

После разрешённого запроса сохранить native receipt и accounting. Если
accounting неопределённо или запрос уже учтён, не повторять его автоматически.
Сохранённую очередь пройти существующими `review-list/review-decide` командами.
Чтение самих внешних источников для проверки объектов тоже требует отдельного
допуска; наличие ссылок в ответе его не заменяет.

Для каждой ссылки оператор фиксирует:

1. Есть ли реальный однозначно определённый объект: адрес/кадастр/разрешение/экспертиза и первичный источник.
2. Актуальны ли стадия и сроки; какие факты ещё не подтверждены или противоречат друг другу.
3. Кто застройщик, заказчик и другие участники; какая организация действительно принимает решение.
4. Есть ли доказанная потребность в алюминиевых конструкциях/остеклении, её срок и основание.
5. Какое следующее действие полезно менеджеру и на каком основании допустим канал. До этого — исследовательская задача, без outreach.

Все решения привязываются к конкретному capture, URL, времени и hash evidence.
Не дополнять отсутствующие данные догадками. Отдельно отмечать дубли,
неподходящие ссылки, устаревшие сведения и ложные утверждения.

| Метрика | Правило |
| --- | --- |
| Найденные ссылки | Количество возвращённых и безопасно сохранённых результатов |
| Дубли | Повторы внутри ответа и существующей истории отдельно |
| Проверенные объекты | Только записи с достаточной подтверждённой идентичностью и актуальными фактами |
| Ложные/неподтверждённые факты | Количество и конкретная причина отклонения |
| Польза менеджеру | Принятые исследовательские задачи и отдельно подтверждённые коммерческие возможности |
| Стоимость объекта | Фактически учтённый расход / число проверенных объектов; при нуле объектов значение не определено |
| Время проверки | Минуты оператора отдельно от стоимости источника |
| Коммерческий результат | RFQ/КП/заказ только с подтверждающим evidence; при отсутствии — «не доказан» |

Один запрос проверяет безопасное прохождение цепочки и даёт небольшой образец.
Он не доказывает стабильный поток лидов или качество по всей стране. Увеличение
объёма и новый job требуют отдельного допуска. До доказанного образца не
подключать второй источник. Затем оценить по одному бесплатные/дешёвые ЕИС,
ЕГРЗ и региональные источники; платный TenderPlan/аналог рассматривать только
после доказанной добавочной пользы и учёта общего месячного бюджета.
